branch-reviewer-sdk — how it works, slice by slice

An AI agent that reviews a GitHub branch and reports findings — built around one uncomfortable observation: a single AI review is a sample, not a survey. Run the same review twice and you get overlapping but different findings. Everything here exists to turn unreliable samples into a trustworthy result: store every run, merge repeats, adversarially verify the one-offs, estimate what's still unfound, and automate the whole loop.

It reads and reports only — it never edits code. And it runs on subscription credit only, enforced in code, so no run can silently bill a pay-as-you-go API key.

review (one run) → store (keep it) → consolidate (merge repeats) → verify (attack the one-offs) → coverage (how much is left?) → campaign (loop until dry) → server (queue it) → trigger (label a PR, it happens by itself)
01

Reviewer — one agent, one branch, structured findings

The core act: point an agent at a branch, let it investigate, get back findings you can compute with.

  • What a review actually is
    • One agent conversation: the model repeatedly picks a tool, reads the result, and digs further until it's ready to report
    • The Claude Agent SDK runs that loop — tool dispatch, retries, validation — so this codebase is only wiring, policy, and the system prompt
    • The target is a branch compared against its merge base: "what did this branch change?", not "what does this repo contain?"
  • The agent sees the repo through exactly three read-only tools
    • list_changed_files, get_diff, read_file — nothing else; every built-in tool is switched off (tools: [])
    • Read-only is a security posture, not a limitation
      • The agent reads untrusted repo content; an agent that can only read can be curious, but not dangerous
    • read_file matters most: good findings rest on evidence outside the diff — a sibling guard, an adjacent cast — so the agent must be able to look around the change, not just at it
  • Findings come back as data, not prose
    • The SDK is given a JSON schema (outputFormat: json_schema) and validates the agent's final answer against it
    • Each finding: file, line, severity (critical / warning / nit), title, detail, suggestion
    • Why it matters: every later slice — storing, clustering, verifying — computes over findings; free text would end the pipeline here
  • The review is honest about its own limits
    • A run that hits its turn budget reports aborted, never a half-finished "success"
    • Exit codes carry the verdict: 0 clean · 1 critical finding (or crash) · 2 aborted
02

Accounting — know what every run costs

Each run burns real credit. Before building anything bigger, make the spend visible — and keep the bookkeeping honest about what it can't know.

  • Accounting is observational, never gating
    • Numbers are reported alongside results; no cost figure ever changes a review's outcome or exit code
    • Why: a reviewer that stops mid-thought to save money produces the worst of both — spent credit and no result
  • Counting tokens from a stream is trickier than it looks
    • Parallel tool calls share one API message id — summing per-event usage double-counts, so the accumulator dedupes by id
    • Input-side figures reconcile exactly against the SDK's final totals; per-message output counts are start-of-message snapshots
      • So the streamed output sum is a lower bound — anything live (like a dashboard) must treat it as one
    • The SDK result's totals are authoritative; the streamed sum only cross-checks them
  • A hard-won stream behavior, handled here once
    • After an error, the SDK yields the result message and then throws
    • The runner keeps that result — it carries the turn count and usage — and only rethrows if no result was ever seen
      • Without this, every aborted run would lose its stats, and aborted runs are exactly the ones worth studying
03

History — runs become data

If one run is a sample, the interesting questions are all cross-run questions — and those need runs on disk, queryable.

  • Every run persists: target, model, status, turn count, cost, token usage, and all findings
    • SQLite via node:sqlite, built into Node ≥ 24 — zero new dependencies
    • Aborted runs persist too, with their stats; failure is data
  • Findings are relational rows, not a JSON blob on the run
    • The whole point is queries like "which findings appeared in more than one run?" — a blob can't answer that; rows can
    • This one schema decision is what makes slices 4–6 possible
  • The database is local-only, deliberately
    • Finding text quotes the reviewed repo's internals — it never belongs in a shared repo
    • data/reviews.db is gitignored; it travels between machines only as an encrypted copy
  • Persistence never changes an outcome
    • A failed save warns and moves on; --no-save opts out — the review's verdict belongs to the review
04

Consolidation — the same bug wears different words

Run a review five times and the same defect comes back with different titles, different line anchors, different framing. Merging repeats is a semantic problem — so a model does the matching, and code checks its work.

  • Why string matching is dead on arrival
    • One defect recurs as "429 handled as fatal" here and "missing retry on rate limit" there, anchored two lines apart
    • Any key built from (file, line, title) treats those as different findings — identity is semantic, not structural
  • An LLM judge clusters findings across runs
    • It's the same machinery as a review, dialed to zero: no tools, one turn, structured output only — pure inference
    • The judge proposes a partition of finding ids; our code enforces it
      • validatePartition checks every id exists and appears exactly once; one retry, with the violation named
      • Trust boundary in one sentence: the model gets the semantic judgment, the code gets the invariants
  • Each cluster carries an occurrence count — "seen in 3 of 5 runs"
    • Occurrence is a confidence badge, never a filter: recurrence and importance are independent axes
      • Proven the hard way: the project's best-ever finding appeared in exactly one run out of many
  • Findings are immutable; clusters are derived
    • Re-consolidating writes a new consolidation row rather than editing an old one — history stays replayable
  • A stochastic component gets its own regression harness
    • A human-verified consolidation is frozen as a golden fixture; eval:judge replays it after any prompt change
    • Kept outside the unit suite on purpose: a judge failure is a signal to inspect, not a broken build
    • Measured stability: independent re-clusterings of the same runs produced identical partitions — which is what lets slice 6 do statistics on cluster counts
05

Verification — attack your own findings

A finding seen once might be a rare catch — or a hallucination. Instead of trusting it, send a second agent whose only job is to prove it wrong.

  • The verifier is a review agent turned against a finding
    • Same three read tools, inverted prompt: gather evidence to refute this claim
    • Only once-seen clusters are verified — findings that recur across independent runs corroborate themselves
  • Verdicts are three-valued, and the third value is the important one
    • confirmed — the refutation attempt found supporting evidence instead
    • refuted — requires positive contrary evidence in the repo, not just a failure to confirm
    • undetermined — the evidence ran out; a human has to look
      • The rule that keeps the system honest: "couldn't refute" must never launder into "refuted" — a binary verifier disguises its blind spots as verdicts
  • Verdicts append, never overwrite
    • Each verification is a new row with rationale, confidence, and cost; the cluster shows the latest
    • So improving the verifier and re-running builds a track record instead of erasing one — and a human verdict can later overrule on top
  • What tuning the verifier taught
    • Verdict instability traced to search coverage, not judgment — the fix was method in the prompt, not vibes
      • Check where overrides actually live (deploy manifests, environment templates) before calling a setting unpinned
      • Follow every conditional guarding a cited path, and name it in the rationale
    • Calibration: 8 of 8 verdicts defensible — including one that refuted a finding believed real, and the refutation held
      • The "known truth" was stale; a verdict is only as good as the evidence it cites — and that cuts both ways
    • Verification costs about 30% of a full review — cheap insurance on exactly the findings that need it
06

Campaign — how many runs are enough?

If each run surfaces some findings, when do you stop paying for more? The campaign answers with ecology's tool for the same question: how do you estimate the animals you haven't caught yet?

  • The loop: review → re-consolidate → check yield → repeat → verify
    • Each round reviews the same branch again, then re-clusters all stored runs of it into one fresh partition
    • When rounds stop yielding novel clusters, stop and verify the once-seen ones
  • A capture–recapture estimator says how much is left
    • The intuition: if new runs keep finding new things, the pool isn't exhausted; if they keep re-finding known things, it nearly is
    • Concretely: the count seen once (f₁) and count seen twice (f₂) estimate the undiscovered remainder as f₁²∕2f₂
    • The estimate is reported, never gating
      • On real data it stays high for many rounds — gating on it would mean never stopping short of the run cap
  • What actually stops a campaign
    • Patience: N consecutive rounds with nothing novel (default 2) → dry
    • A hard run cap, as the backstop
    • Two consecutive aborted rounds → structural problem; more rounds would burn credit, not find bugs
  • Two design details that save real money
    • Rounds fire back-to-back in one process, so each rides the previous round's prompt cache
      • Fresh input drops to a sliver against millions of cached tokens — spreading rounds over days would pay full price every time
    • Verdict inheritance: a new consolidation's cluster with an identical member set inherits the existing verdict instead of re-paying for verification
      • Motivated by a campaign that re-spent ~$5 re-adjudicating already-settled findings; --reverify re-tests deliberately
  • Why novelty is measured inside one partition
    • Comparing cluster counts between two separate clusterings would measure the judge's mood, not the branch — one partition, one yardstick
07

Headless auth — the money guardrail

Everything so far runs where a human logged in. To run unattended on a server, the system needs credentials — without ever opening a second, silent billing path.

  • The invariant: subscription credit only, enforced in code
    • assertSubscriptionCredit() refuses to run at all if ANTHROPIC_API_KEY or ANTHROPIC_AUTH_TOKEN is set
    • Why refuse instead of prefer: credential precedence is undocumented — the only safe assumption is that a present API key might win, and a run must never silently bill pay-as-you-go
  • The one blessed credential: CLAUDE_CODE_OAUTH_TOKEN
    • Minted by claude setup-token — subscription credit by construction, so it's the deliberate exception to the refusal list
    • The mint is an interactive browser OAuth flow: run it once in a real terminal, put the token in .env, done
  • Unauthenticated failure is weirder than you'd expect — so it's translated
    • The SDK reports "not logged in" as subtype: 'success' with is_error: true, then the stream throws
      • Downstream code expecting structured output would die on a confusing parse error instead of the real cause
    • A shared throwIfErrorResult() catches the shape everywhere and tells a headless machine the actual fix: run claude setup-token
  • Proven, not assumed
    • Acceptance: a full review completed with HOME pointed at an empty directory — no login state visible, only .env credentials in play
08

Server — reviews become jobs

A CLI does one thing while you watch. A server accepts work, survives restarts, and must never lie about what happened while you weren't looking.

  • A durable job queue, in the same SQLite file as the runs
    • A job is a request — "review this branch", "run a campaign" — with a full lifecycle on disk
    • States: queued → running → succeeded | aborted | failed, plus queued → cancelled
      • Cancel only works on queued jobs — a running job has already spent credit
      • Every transition checks its expected prior state; an illegal move is an error, never a silent no-op
  • One worker, strictly sequential — a feature, not a bottleneck
    • Subscription credit is a serial resource; parallel jobs would race each other for it
    • Back-to-back runs of one target ride each other's prompt cache — sequence is literally cheaper
    • Job outcomes map through a fixed error taxonomy
      • Transient (network, overload) → retry candidate · terminal (auth, bad branch) → fail fast · capped (turn budget) → aborted, run still saved
  • Honesty about interruption
    • A job found running at startup was orphaned by a crash — it's marked failed, never silently re-run
      • A re-run bills credit; spending money is a human decision
    • Unlike the CLI, a failed save fails the job — a server job's result is only reachable through the store, so "saved" is part of "succeeded"
  • The HTTP surface is deliberately small
    • Hand-rolled on node:http — four routes don't earn a framework
    • Request policy lives in the request schema: defaults and validation in one Zod shape, unknown fields rejected with a precise error
    • Binds 127.0.0.1 only and has no auth — safe because unreachable; exposure is a future, deliberate step
09

Trigger — label a PR, the rest happens by itself

The last mile of automation: nobody calls the API. Put a label on a pull request, and the next poll cycle turns it into a review job — with the spend still under human control.

  • Polling, not webhooks
    • Webhooks need a reachable server and auth — neither exists yet; polling works behind NAT with the token already in hand
    • The job model doesn't care which one feeds it, so webhooks can replace polling later without touching anything downstream
  • A watch = "poll this repo for this label"
    • Stored as database rows, managed over HTTP — a committed config file would leak which repos get reviewed
  • Cost stays opt-in twice over
    • Only open, non-draft PRs carrying the trigger label are considered — the label is the request, and removing it stops future triggers
    • One job per head commit SHA: a new push re-triggers only while the label stays on
    • The job pins the SHA, not the branch name — it reviews exactly the code state that carried the label, even if the branch moves
  • The jobs table doubles as the trigger's memory
    • Any existing job for (owner, repo, SHA) — in any state — blocks re-enqueue
      • A failed job is never auto-retried, a human's cancel is never overridden, and there's no separate "seen SHAs" table to drift out of sync
  • Safety valves for a thing that acts on its own
    • A per-cycle cap on enqueues across all watches — a mass labeling event can't drain the budget in one poll
    • Overlapping poll passes are skipped: two concurrent passes could both see a SHA as new and double-enqueue
    • One misconfigured watch logs its error and the others keep polling
  • Proven end-to-end, both the free and the paid path
    • Free: a watch on a busy public repo (79 open PRs, none labeled) enqueued nothing, cycle after cycle
    • Paid: a label applied to a real PR auto-enqueued on the next cycle, reviewed unattended, and the following cycle skipped the SHA — no duplicate
∑

The whole machine — one PR, start to finish

Everything above, replayed as one story.

  • You label a pull request agent-review
    • Within a poll cycle, the trigger sees it, pins the head SHA, and enqueues a job — unless that SHA was ever seen before
  • The worker picks the job up, alone and in order
    • A review agent explores the branch through three read-only tools and returns schema-validated findings
    • The run persists with its cost and turn count — succeeded, aborted, or failed, it's all recorded truthfully
  • For a campaign, the loop takes over
    • Rounds repeat while they yield novel clusters, riding the prompt cache; consolidation re-merges every run into one partition after each round
    • The estimator reports how much is likely still unfound; patience decides when to stop
  • Trust is earned per finding
    • Findings seen in several runs corroborate themselves
    • Findings seen once get an adversarial verifier — confirmed, refuted with evidence, or handed to a human as undetermined
  • What you read at the end is not "what one AI said"
    • It's the union of independent samples, semantically deduplicated, adversarially tested, with a coverage estimate attached
      • That artifact — not any single run — is the review
